Document generation code: `lib/admin/docs/invoice-pdf.ts` (pdf-lib, PDF), `lib/admin/docs/agreement-docx.ts` / `scope-docx.ts` (docx package), shared logo/spacing helpers in `lib/admin/docs/docx-helpers.ts`, shared project-tracking code generator in `lib/admin/docs/document-code.ts`.

**Confirmed safe (2026-09-13 review) — do not re-flag unless the code changes:**
- All font/template/logo file paths (`require.resolve('@fontsource/...')`, `path.join(process.cwd(), 'public', 'invoice', 'Invoice Template.png')`, `path.join(process.cwd(), 'public', 'Logos', 'Kyfaru Logo-08.png')`) are fixed constants — no request-controlled input ever reaches a filesystem path in this code. No path traversal / arbitrary file read possible here.
- All document generation is purely in-memory: `pdf.save()` → `Uint8Array`, `Packer.toBuffer(doc)` → `Buffer`, both streamed directly as the HTTP response body. Nothing is written to disk, and specifically nothing is ever written under `public/` (checked: no `writeFile`/`createWriteStream` anywhere in `lib/admin/docs/*`). `public/invoice/Invoice Template.png` and `public/Logos/Kyfaru Logo-08.png` are blank/static input artwork, not generated output — they never contain client PII.
- `getOrCreateDocumentCode(projectId)` in `document-code.ts` uses Drizzle's `sql` tagged template with `${projectId}` and `${monthCode}` interpolated — confirmed via `node_modules/drizzle-orm/sql/sql.js` that plain-value interpolations become bound query parameters (`$1`, `$2`, sent to the driver separately), NOT string-concatenated into SQL text. Only `${projects}` (a `Table` object) renders as a raw escaped identifier, which is safe because it's a hardcoded import, not user data. This pattern (interpolating a plain JS value into `sql\`...\``) is Drizzle's standard parameterized usage — not injection-prone by itself. Only worry if someone uses `sql.raw(...)` with user input, which is different and dangerous.

**New behavior worth remembering:** `getOrCreateDocumentCode` does a real UPDATE (consumes a global Postgres sequence, persists `projects.document_code`) as a side effect of a GET request (`agreement-pdf`/`scope-pdf` routes). **Partially fixed as of 2026-09-13:** both routes now gate this behind `requireRole(role, 'manager')`, so it's no longer "any authenticated user" — only manager+ — but still no per-project ownership scoping (any manager+ can trigger it for any project), consistent with [[kyfaru-admin-authz-model]]'s org-wide-access convention.

**`ProjectRequirementsDoc`/`scopeDocument` jsonb — no runtime validation (confirmed 2026-09-13):** `lib/admin/types/project-requirements.ts`'s `isRequirementsComplete()` and the `scope-pdf`/`agreement-pdf` routes both do direct property access (`doc.purpose.trim()`, `doc.pages.items.length`, `reqs!.hosting.provider`, etc.) on the jsonb column cast with a bare `as ProjectRequirementsDoc | null` — no Zod schema anywhere validates the shape. `app/api/admin/projects/[id]/route.ts`'s `PATCH` added `scopeDocument` to its editable-fields array with zero validation (`updates[k] = body[k]`, same pattern as every other field on that route — not a new gap specific to this field, just extending an existing unvalidated-PATCH pattern to a nested-object field for the first time). A manager+ caller sending a malformed/partial `scopeDocument` (missing `hosting`, `pages`, wrong types) would pass `isRequirementsComplete`'s `!doc` check but then throw a TypeError (500) inside it or inside `buildScopeDocx`. Availability/robustness issue, not an injection risk (confirmed: `docx` package's `TextRun`/`Paragraph` API is used exclusively for all scope-doc/agreement-doc text — no raw XML string concatenation anywhere in `scope-docx.ts` or `agreement-docx.ts`, so no document-injection vector even with attacker-influenced string content).
