Kyfaru's `components/admin/shared/DatePicker.tsx` wraps `vanilla-calendar-pro@3.3.2` directly (not Preline's `HSDatepicker` wrapper around the same engine — that wrapper's compiled bundle throws `ReferenceError: _ is not defined` under Turbopack due to an unbundled lodash-global reference in Preline's own build).

**Supply-chain: clean, confirmed 2026-09-13.** `node_modules/.pnpm/vanilla-calendar-pro@3.3.2/.../package.json` has real `repository`/`homepage`/`bugs` (github.com/uvarov-frontend/vanilla-calendar-pro), MIT license, and genuinely empty `dependencies: {}` / `devDependencies: {}` / `scripts: {}` (no lifecycle/postinstall scripts). pnpm-lock.yaml resolves it as a normal npm-registry package with a `sha512` integrity hash (no git/tarball override). Skimmed `index.mjs`: no `eval`/`new Function`/network calls/cookie or storage access.

**sanitizerHTML defaults to a no-op identity function** (`__publicField(this,"sanitizerHTML",(e=>e))`). The library uses `innerHTML` internally in several places (day-grid layout, time-picker markup, custom day popups via a `popups`/`dataPopups` option, and a range-tooltip via the `onCreateDateRangeTooltip` callback) but always routes through `sanitizerHTML` first — which does nothing by default. **Kyfaru's current `DatePicker.tsx` never sets `popups`, `layouts`, `labels`, or `onCreateDateRangeTooltip`**, so none of those sinks currently receive any data at all, let alone untrusted data — confirmed a non-issue as of this review. But if a future feature ever wires a user-controlled string (e.g. a note, a client name) into any of those four options, it becomes instant DOM-based XSS unless an explicit `sanitizerHTML` (e.g. DOMPurify) is configured. **How to apply:** when reviewing any future `DatePicker.tsx` change that adds `popups`/`layouts`/`labels`/`onCreateDateRangeTooltip`, check what feeds them and require `sanitizerHTML` to be set if any of it is user-controlled.

**`DatePicker.tsx`'s own DOM write is safe:** it does `inputRef.current.value = dates.join(' - ')` inside `onClickDate` — plain `.value` property assignment to a `readOnly` text input, not `innerHTML`. This is cosmetic display only; actual form submission in all 4 call sites (`ProjectFormDrawer`, `ExpenseFormDrawer`, `InvoiceFormDrawer`, `UserSlideOver`) reads from React state set via the `onChange` callback, never from the DOM node directly.

**Range mode auto-sorts, so a reversed (from > to) range can't be produced through the picker UI itself:** `vanilla-calendar-pro`'s `multiple-ranged` selection mode sorts `selectedDates` chronologically (`n.sort((a,b)=>+new Date(a)-+new Date(b))`) after every click, regardless of click order. So `UserSlideOver.tsx`'s access-window picker (and any other range picker) cannot hand the parent a reversed pair via normal clicking — this is actually a UX/data-quality improvement over the two independent native `<input type="date">` fields it replaced (those had zero ordering enforcement). The underlying API routes (`app/api/admin/users/route.ts`, `[id]/route.ts`) still have no server-side ordering/format validation at all — pre-existing gap, see [[kyfaru-admin-authz-model]] — but it's not something this UI change makes worse, since a non-UI caller (curl/Postman) could always submit a reversed pair regardless of what the picker allows.

**Multi-instance isolation confirmed non-issue:** each `Calendar` instance owns its own `context` object (own `mainElement`, own click-outside document listener closing over that specific instance). `inputMode: true` attaches the popup element to `document.body` (or the nearest root node, for shadow-DOM support) but there's no shared/global mutable state — two simultaneously-open `DatePicker` instances don't cross-contaminate.
