Kyfaru (F:\Web Dev\Kyfaru) is an internal admin/CRM tool (NextAuth v5 + Drizzle/Neon Postgres), not the SILQU tenant-facing product. Role hierarchy lives in `lib/admin/permissions.ts`:
`viewer | communications | tech | finance | sales` = tier 1, `manager` = 2, `admin` = 3, `super_admin` = 4. `requireRole(role, required)` throws a plain `Error` on failure (uncaught in route handlers → Next.js returns a generic 500, not 403, when a role check fails — cosmetic, access is still denied).

**Systemic gap (confirmed as of 2026-09-13, pre-existing, not introduced by any single diff):** many admin API routes check only `session?.user` (any authenticated user, any role) with zero resource-level ownership/tenant scoping:
- `GET /api/admin/invoices`, `GET /api/admin/projects`, and the new `GET /api/admin/projects/[id]` (added in the phase 6-9 batch) all return full rows (incl. client PII, quoted amounts, `scopeDocument` contents) to any authenticated user, any role, no filtering — consistent with each other and with `POST /api/admin/reports/[reportId]` (also session-only, no `requireRole`), so this is an established convention in this codebase, not a one-off oversight in the new route.
- `GET /api/admin/invoices/[id]/pdf` — still only checks `session?.user`, no `requireRole`, no per-client scoping (as of 2026-09-13, unchanged by the phase 6-9 diff — that diff only removed two unused hardcoded fields from this route).
- **Fixed as of 2026-09-13:** `GET /api/admin/projects/[id]/agreement-pdf` and `.../scope-pdf` now DO call `requireRole(session.user.role as Role, 'manager')`, confirmed to run immediately after the session check and before the `isRequirementsComplete`/`getOrCreateDocumentCode` logic added in the same diff. No probing-before-auth issue. Still no ownership scoping (any manager+ can hit any project's doc), but that matches this app's org-wide-access model.
- `app/admin/(app)/notifications/page.tsx` does an unscoped `select().from(notifications)` — shows every user's notifications (including ones with a specific non-null `userId` targeted at someone else) to any logged-in viewer.
- The new `app/api/admin/projects/[id]/activity/route.ts` (session-only, no `requireRole`) is a good example of the right way to expose audit data under this model: it returns only `{id, icon, title, time}` per entry — explicitly omits `before`/`after` snapshot content — matching the same restraint `reports/[reportId]`'s `case 'audit'` uses (selects only action/entityType/entityId/ip/createdAt, never before/after). Treat this omission as the established convention for any future audit-log-exposing route in this codebase.

**How to apply:** When reviewing any new Kyfaru admin route touching client/project/invoice data, check for a `requireRole` call AND a row-level ownership/scope check — most existing routes have neither beyond "is logged in." Flag missing ownership checks as pre-existing/out-of-scope unless the diff being reviewed is the one introducing the route or changing its auth logic. See [[kyfaru_docgen_conventions]] for the specific document-generation routes this was last confirmed on.

**Critical, confirmed 2026-09-13 — `accessType`/`accessFrom`/`accessUntil` on `users` are decorative, not enforced (pre-existing, predates the DatePicker refactor):** the schema (`lib/admin/db/schema.ts`) and both `app/api/admin/users/route.ts` (POST) and `app/api/admin/users/[id]/route.ts` (PATCH) read/write these fields with **zero validation** (no Zod, no check that `accessFrom <= accessUntil`, `new Date(rawString)` fed straight to Drizzle). Worse: nothing in the login/session path ever reads them — `lib/admin/auth.ts`'s `authorize()` only checks `user.isActive` + bcrypt match, `lib/admin/auth.config.ts`'s `jwt`/`session` callbacks never touch them, and the edge middleware `proxy.ts` only checks `isLoggedIn` + 2FA state. So setting a "custom" access window in the admin UI (`UserSlideOver.tsx`) has no effect on whether that account can authenticate, at login or across its 8-hour JWT session — it's a pure UI/data illusion. This is a real Broken Access Control / Broken Authentication gap (OWASP A01/A07) but is NOT something the `components/admin/shared/DatePicker.tsx` introduction changed — it already existed with the old native `<input type="date">` fields. Flag as pre-existing-critical whenever `accessFrom`/`accessUntil`/`accessType` come up; the actual fix belongs in `authorize()` (and ideally a periodic/edge re-check for already-issued sessions, since JWT sessions aren't re-validated against DB state until they expire).
