Reviewed the new `components/admin/shared/DatePicker.tsx` (wraps `vanilla-calendar-pro@3.3.2` directly, bypassing Preline's broken `HSDatepicker`) and its integration into ProjectFormDrawer, ExpenseFormDrawer, InvoiceFormDrawer, UserSlideOver. Uncommitted at review time. No files were edited — review only.

**Real bug found (highest priority, unconfirmed live — dev server was down):** the "sync effect" pattern (an `Effect 2` keyed on a serialized `valueKey`, guarded by a `lastEmittedRef`, meant to catch up when the `value` prop arrives async) has a gap distinct from the one it was built to fix. `Effect 1` (`useEffect(() => { import('vanilla-calendar-pro').then(...) }, [isRange])`) closes over `props` from whatever render scheduled it and is never re-invoked unless `isRange` changes — so if `Effect 2` fires with a new `valueKey` while `calendarRef.current` is still null (import pending), it no-ops WITHOUT updating `lastEmittedRef`. When the import later resolves, `Effect 1`'s stale closure initializes the calendar with the ORIGINAL (often null) value and marks that stale value as "already emitted" in `lastEmittedRef` — permanently masking the real value from ever syncing, since nothing will re-trigger `Effect 2` unless the prop changes yet again.
This is not just a rare network race: `Drawer.tsx` conditionally mounts children only when `open` (`{open && (...)}`), and ProjectFormDrawer/ExpenseFormDrawer/InvoiceFormDrawer populate `form` from an existing record via `useEffect(() => { if (open) setForm(fromRecord) }, [open, project])` — meaning DatePicker's first render always sees a null value, and the real value arrives one synchronous effect-cascade later, which (being synchronous) is essentially guaranteed to complete before the dynamic `import()` promise's `.then()` can run (promises can't preempt a synchronous call stack). So this can misfire on ordinary "open the edit drawer" — worth an actual live re-test (dev server was returning a bare-text "Internal Server Error" on all 3 running ports at review time, unrelated to this diff, blocking empirical confirmation).
Fix direction: keep a `latestPropsRef` (or `latestValueRef`) updated every render, and have `Effect 1`'s `.then()` read from that ref instead of its stale closure, so whichever value is current when the calendar actually mounts gets applied — collapsing both the already-tested "slow fetch" race and this "synchronous mount cascade" race into one code path.

**Real behavior gap, not a crash:** `vanilla-calendar-pro`'s `enableDateToggle` option defaults to `true` (confirmed in compiled source: `__publicField(this,"enableDateToggle",!0)`), and `DatePicker.tsx` never overrides it. Consequence: clicking the same day twice does not produce a sensible `{from: X, to: X}` single-day range in range mode — `handleSelectDateRange`'s toggle branch fires and resets `selectedDates` to `[]`, so the component's `onClickDate` emits `{from: null, to: null}`, silently clearing the whole selection. Same root cause also means clicking an already-selected day in SINGLE mode (`handleSelectDate`) deselects/clears it — relevant for InvoiceFormDrawer's `required` due-date field, which has no inline re-validation until save. Fix if single-day ranges are desired: pass `enableDateToggle: false` in the Calendar options for range mode.

**Minor/defensive findings:**
- `calendar.init()`'s return value (a listener-cleanup function per the lib's own `.d.ts`: `init: () => () => void`) is discarded. Currently harmless because `destroy()` achieves the same end a different way (`inputElement.replaceWith(clonedOriginal)`, which drops listeners since `cloneNode` never copies JS listeners) — verified by reading the compiled `destroy` function — but it's incidental, not contractual. Recommend capturing and calling it defensively.
- `destroy()` never calls `hide()` and never drains `context.cleanupHandlers`, so destroying the calendar while its popup is open leaks a `window resize` + `document keydown` + `document click(capture)` listener. In practice, nearly every real way of closing the drawer while the calendar is open (clicking the X, clicking the backdrop, pressing Escape) itself fires a click/keydown that the calendar's own capture-phase "click outside" listener intercepts and cleans up via `hide()` before the drawer's own handler runs — so the window is narrow (programmatic close with no user gesture). Cheap hardening: call `calendarRef.current?.hide()` before `.destroy()` in the effect cleanup.
- Portal-code revert (a previously-tried, since-reverted document.body-portal workaround) is fully clean: grepped the whole `components/admin` tree for `wrapperRef`, `portalCleanup`, `createPortal`, `document.body` — zero matches, no dead imports.
- Discriminated-union casts (`as SingleProps`/`as RangeProps`) and the `min`/`max as DateAny` casts are safe: whole-project `npx tsc --noEmit` passes with zero errors, and `getDate = e => new Date(\`${e}T00:00:00\`)` in the compiled lib confirms a plain `"YYYY-MM-DD"` string is parsed and actively enforced (used in month/year nav + day disabling), not silently ignored.

Useful mechanics for next time: `vanilla-calendar-pro`'s published package is minified to one line per file (`index.mjs`/`index.js`); to read it, `s.replace()`-insert newlines or just `indexOf`/slice around a keyword via a quick `node -e` script rather than trying to grep it directly. Package lives at `node_modules/.pnpm/vanilla-calendar-pro@3.3.2/node_modules/vanilla-calendar-pro/` (pnpm symlink structure). This repo has no test framework installed yet (no vitest/jsdom/happy-dom in package.json at review time) — a live browser (claude-in-chrome) is the only way to empirically verify component behavior here.

Also: at review time, all 3 already-running dev servers (ports 3000/3001/3002) returned a bare-text (non-HTML, non-Next-overlay) "Internal Server Error" on `/admin` and `/admin/login`, and a fresh `next dev` on another port refused to start (`.next/dev/lock` held). Unrelated to the DatePicker diff — likely fallout from the other uncommitted changes in the tree at the time (schema.ts, invoice-pdf.ts, deleted template files). Worth checking before relying on live browser verification in this repo again.
